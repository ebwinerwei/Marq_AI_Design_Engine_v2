# Marq AI Design Engine｜工作台 2.0 升级实施与验收方案

**株式会社ブルーライト · 内部开发评审稿 · 2026-11-17**  
业务依据为本次上传的《Marq_AI_Design_Engine_Master_Proposal-2.docx》。技术基线为指定的《Marq 外墙排板工作台 2.0 完整包》。本文供确认范围和实施次序，本轮交付仅为本文件。

## 1　建议批准的技术路线

**保留 2.0 的本地工作台，另建可独立启动的 M.A.D.E. 工程工作台。先证明同一栋楼的每一块板都能追溯到设计依据，再让 CAD、采购、营业提案和 CG 团队共用这一版结果。** 现有工作台已经解决了导入、选墙、着色、部分排板和本地演示。新增投资最应放在可验证的工程几何、例外规则和批准流程上。独立入口略增加维护工作，换来可随时回到 2.0 的部署边界；规则达到等价后再评估共享代码。

| GLP 的业务问题 | 新流程落点 | 实际验收人和证据 |
|---|---|---|
| 柱跨、层高、开口变了，设计师要逐墙重排 | 建筑师提交批准的立面和构件；系统仅重算受影响的展开组，标出增删板及原因 | 设计师在变更前后图中核对板号、起点、洞口和相邻面 |
| CAD、CG、色占比和报价来自不同版本，会上难以定案 | 选中方案版本后，同时查看全周 3D、单面占比、材料量和同视点比较图 | 开发、营业和客户围绕同版 A/B 方案选定，导出的图表带同一结果标识 |
| 规则解释靠少数人，难以跨项目复制 | 规则逐条附出处、适用范围、例外和批准人；历史项目锁定当时版本 | 指南制定者审规则，项目负责人审方案，管理层查看采用率和实际节省 |

**“100%”的验收口径。** 经 GLP 签认的明确规则，逐条有实现、基准答案和可重复通过的测试；需要审美、现场判断或采购确认的条目，逐条有输入人和批准记录。发布门槛是全量必测项通过、未决阻断项为零。测试不能预先证明未来所有输入都零缺陷，工时、交期和投资回收按真实案件测量。建筑规模、结构、消防设计、门窗、排烟、楼梯及设备位置沿用建筑师批准的设计，系统处理其对饰面、可视化和数量的影响。

### 上线前必须关闭的三个具体差异

1. **C4、C6 位图有文字与代码分歧。** 从左起 1 基，Word 写 C4＝2,5,7,13，2.0 为 2,5,7,12；Word 写 C6＝1,3,5,6,8,9,13，2.0 为 1,3,5,6,8,9,12,14。把主指南 P.18 原图、Word 定义和代码渲染并列给制定者签认。逐位签出 A/B 各 7 项、C 共 9 项及方向。C6 两种结果连面积也不同。历史版本继续以旧规则重现；批准后在新版本发布差异说明。
2. **顶排租户带已有可复现边界错误。** 输入 H、板宽 750、柱跨 9000、墙宽 1,489,500 mm（331 个半跨）、层高 [6500,7100,8300]、横排租户、无标识无掩码，2.0 读取不存在的位图并抛 TypeError。租户顶段逻辑在跳过区仍计算负序号，只加一次序列长度不足以保证非负。新引擎先生成独立顶段，再从下一段序号 0 启动；合法序号按序列长度循环。加测刚好等长、等长加一、超过两周期及单段楼。大墙在约定规模内应正常计算，超过上限时返回可读提示。
3. **逐面配色与数量是两个工程口径。** 现有计算用所有输出片段汇总百分比；面 A 超限可能被面 B 稀释。一块原板被洞口切成数行 CSV，跨面又可能重复同一 id。先确认原板、实际下料件、表面区域与采购计量单位，再编写 BOM。屏幕 Canvas 分辨率与采购面积无关。

## 3　从建筑师交付到 GLP 批准的一次真实操作

1. 设计师新建项目，选 dry/CS、BOX/ランプ、板材働き幅、规则版本。上传已确认的立面图作为底图，或导入 FBX/GLB；平面与立面缺少语义时由设计师标注。仅有图纸的项目通过标注面轮廓和洞口生成简化体量供审查，记录模型精度。
2. 录入轴网、各跨长度、楼层标高和女儿墙；核对两点已知尺寸、立面向外法线和一个已知角点。依次点选起铺点、张贴方向、需要连续的面，标注标识、门窗、坡道和例外。自动建议逐项可确认，显示源图对应位置。
3. 系统生成基准案；设计师可输入“入口周边留白、上层强调、临街面特注色不超过本项目核定上限”。AI 将意图转为候选参数，用户能看见哪些条件发生变化。规则核重新计算并验证；冲突显示具体面、原因和可调整项。
4. 与基准案同机位、同光照比较；查看颜色分布、净面积、材料费用差和规则解释。营业人员可复制出 BTS/租赁洽谈案。已批准设计、几何与规则包仅授权者可变更。
5. 审核通过形成冻结修订。DXF、XLSX、工程模型、客户说明、空拍合成和 CG 委托均引用同一结果。建筑师调整窗口后，旧修订仍可回看，系统标出受影响的板、报价和已过期输出，重新审签。

## 4　六项核心功能的实现合同

### F1　任意楼层、逐跨轴网和真实几何（Word §4.1）

工程输入采用毫米、明确模型单位和坐标系。每墙保存有向局部坐标 U/V、边界多边形、孔洞、相邻墙边、所在楼层集合和校准变换；每个展开组保存有序墙 ID、连接边、投影方向、逐跨尺寸和起点。允许两墙转角、错台、局部退台和不同顶标高。对未成环轮廓、零面积、重叠墙、跨组不连续、单位不明分别定位，允许预览，阻止受影响的正式输出。设计师确认后才把测量值写入工程记录。

| 模块 | 排布和方向 | 最小验收例 |
|---|---|---|
| A | 横贴、h≤750；当地实际柱跨/2 宽、12h 高；位图按上至下 | 750×12＝9,000 高、9,000 跨得 4,500 宽；600 得 7,200 高 |
| B | 横贴、h>750；当地实际柱跨/2 宽、8h 高 | 900×8＝7,200 高、7,200 跨得 3,600 宽；750/751 验证边界 |
| C | 竖贴、15h 宽、高为本层实际排板高度；位图按核准墙面方向 | 750×15＝11,250 宽；三层分别 6,500/7,100/8,300，不取平均 |

跨宽与 15h 不整除时，明确连续序列的裁切点，避免每根轴线误重启；非标准情况由 GLP 选定规则。横贴按当地轴网生成各列，顶部排满再裁末端，不把末板拉伸。女儿墙独立标注归属和饰面，不能默认算成一层。单层、人为划分的夹层、1～N 层、异层高均走同一模型；技术容量由面数、板数、内存和实测决定，与六阶段规则独立。

### F2　数字序列与竖贴三步求解（§4.2）

**标准序列。** 用现有 329/265 位和批准的位图生成编号格。右上品牌标识面从右上向左；左上、中央、无标识及两面整合从左上向右。每段回到起侧向下续排，超长循环。将“模块走向”和“模块内部位图是否镜像”分别存储，以指南示例的首尾板核定，避免因扫描方向反转而误翻图案。人工指定的开始面与方向同默认规则冲突时记录偏离依据和批准人。P.39 的 35 跨×8 模块横贴示例用于基准比对。

**三步模式。** ① 取物理柱跨数，≤10 跨建议 1 处余白，11–19 跨 2–3 处，≥20 跨 3–4 处。以标识和入口为锚点生成连续余白区，0 强制银、1 可作过渡；最小视觉宽度和非周期判据由制定者校准。② 在强调区选择或组合山並み 234565432、双峰 234323432、鞍型 654323456、台地 234555432、尾根 234567，允许已核准的自定义序列；检测 2525 型反复。③ 按层高/楼序产生顶强底弱的候选，重号按规则调整下层并继续向下复核，强制留白不出现负数。单层免做层间比较。仅在适用的强调区检查重号，阈值和软性构图标准留给制定者批准。

**确定性约束求解。** 固定输入、规则版本、候选次序和种子应得同一结果。逐候选执行全部例外后再算各面面积、特注色限额及成本；在有限预算内选择满足硬约束且最接近设计意图的候选。输出“已找到可行案／已证明约束冲突／搜索限时未找到”三种可区分结果；后两种保留上次有效方案，显示锁定板、冲突条件和可修改参数。人工微调可锁定，解锁或例外须显式操作。面积上限 20% 仅为演示值，按案件录入地区、适用面、分母、色相/明度/彩度、来源、生效日和审核人；RGB 近似色不直接推导条例结论。无批准依据时显示“景観条件未確認”。

### F3　六阶段建筑特例（§4.3）

六阶段作用于构件和板件，每一层楼均可适用。输入构件分为真实开口、实墙、设备遮挡、未来开口板、标识、坡道等。几何扣除、换色、局部换位和图形覆盖分别计算。最终实洞从材料域中永久扣除，银色覆盖不能把洞补回去。

| 阶段 | 输入和确定性处理 | 项目级验收 |
|---|---|---|
| S1 两面整合、雁行、切欠 | 在所选主角连续展开；正对可见的错台共用投影基准；短正交面和符合条件的切欠刷银。无法按比例或可视性自动归类的面提示协商 | 两面共享角不断号，非相邻面拒绝拼接；侧面保持独立几何，超常比例面有确认记录 |
| S2 租户横排 | 分离最上 1 模块银带，其下从序列首位起排；不足一模块时按批准裁切策略处理 | 检查顶段、第二段第一编号和长墙异常例；两种铺法均测 |
| S3 品牌与租户标识 | 角部横贴 4×1.5、竖贴 2×1.5 模块，两侧均适用；非角部以实际标识中心展开 6×1.5 / 3×1.5；标识上部留 M 字宽。租户纵列按批准尺寸延伸 | 用原标识资产和 Sign Manual 校核 M 宽、锚点、窄面边界及银底。资料不足时预览并标记待审 |
| S4 窗、设备、楼梯 | 横贴或仅一层连窗作实洞；竖贴各层连窗在其实际宽度内移排，使窗顶对齐模块下边。未来开口或排烟窗相交触发整块原板换银，再按构件类型扣实际洞。设备阳台、外梯、竖管、风机单独标注遮挡/背墙饰面 | 比对局部连窗两端，窗外列不移；设备遮挡区可有实际背板。材料计量与有效可视面积分开 |
| S5 坡道与车路 | 以坡道边线和腰壁实际见付高定位。腰壁 F19-30A，中央 Electric Blue 带宽 14–20%；檐下车路壁 19-60A、柱 F19-20B。横贴沿坡阶梯切、竖贴斜切，下缘加扁钢等收边对象 | 两端和坡中测带宽，导出切边及收边长度；附节点和材料规格经设计师签认 |
| S6 月台编号 | 按批准的月台清单排序，以开口上中点和一层外壁为锚，黑底白字。支持 001 起、既有编号、跳号和人工锁定 | 验证一门一号、转角不重复、移门后同号跟随，清单、立面和模型一致；字体尺寸按标识手册 |

所有操作附源条款和 ruleId。先建立展开拓扑与洞口原始几何，再求基础编号与局部移排，生成物理板，施加换色、净几何裁切，再附加腰线、收边和标识。阶段名称用于向设计师解释，执行依赖按此顺序实现。至少用“租户银带＋角标＋跨层窗＋未来开口”重叠样例检验优先级、去重和可追溯性。

主数据带厂家、产品系列、铺向、颜色、有效日期、板长/加工约束、报价来源。三家是备选供应方案，各家独立成表，不能合计成三倍材料。未收录组合及特注色列入询价；报价过期或缺料号时显示差额未确定。项目报价由采购人员确认。

**统一计量。** 每块板分配 stockPanelId，每个切件有 pieceId，饰面子域有独立 ID；板缝、跨墙生产分板、裁切、损耗、备料和最大板长均须指定。净面量＝面轮廓与实际成品交集减去真实开口并集；饰面不同部分分别记账。示例：一块 4,500×750 板被 1,000×500 窗洞切入，若洞完全位于板内，余下面积 2.875 m²；可能形成多条图形记录，预算毛板仍按经确认的下料计划计数。无下料规则时可给净量与理论件数，正式采购栏标“待深化”。逐面色占比用最终强调饰面与项目批准分母；同时报全楼汇总、特注费用、厂家最低批量和预算差异。缺单价不按零元。

**XLSX 工作簿。** 案件和规则版本、逐面净量、板件/切件明细、三厂家对照、特注及缺项、估算条件和审核页。CAD、3D、XLSX 共用板 ID；从总量点回板件，任取一块可回到对应立面。

### F5　全周 3D、空拍融合、项目实景与设计说明（§4.5、§5）

- 工程结果驱动外墙、门窗、标识、坡道、植栽与入口的独立图层。WebGL 提供同机位比较、环境光、方向光方位/高度、阴影、日/夕/夜；保存曝光、相机和材质版本。软件渲染保留简化查看，复杂模型采用轻量代理或分块加载。工程坐标和用于显示的缩放矩阵单独保存。
- 生成空拍或街景方案图时，上传已授权影像，记录相机、消失点、地平线、比例、光照及模型落地点。输出建筑 RGBA、深度、对象/材质 ID、阴影和前景遮挡。先确定性合成锁定建筑；商用图像服务在允许区域处理环境、天空或植栽。需要金属反射时保留确定性材质重渲染通道。保护区重新合成原建筑，校验轮廓、板缝、Logo 和颜色 ID；缺深度、模型不受支持或服务超时均可交付本地预览。15 秒为测试目标，界面可取消、排队、重试。
- 图案说明从已算出的余白、节奏、层间强弱、开口、配色和面积生成日文草案，区分“图案构成事实”与“设计寓意”。保留规则模板供离线使用。例：“エントランスまわりにシルバーの余白をまとめ、上層にアクセントを寄せました。遠景では壁面にリズムを与え、近景ではサインを読み取りやすくする意図です。” 仅在事实匹配时可选用。AI 文字/图片均不能回写工程板位和订货数量。

### F6　DXF、工程 3D 与一键 8K 专业 CG 委托（§4.5、§6）

- **DXF** 按已批准的模型空间毫米坐标输出各面真实尺寸展开图，含轴线、标高、面轮廓、孔洞、板缝、色填充、标识、收边、尺寸及板号，分层且支持日文。图签记录 revision、单位、比例和设计阶段。以 1:1 模型空间回读，并由客户使用的 AutoCAD 实测两条已知线段、洞口坐标和闭合区域净量。
- **工程 3D** 生成真实比例 GLB（米），随附毫米工程坐标、原点、轴向及变换；交付前从导出的 GLB 反测已知轴距。展示 GLB 沿用旧用途。权属受限的素材只传引用和使用说明。
- **8K 委托** 授权人员在已批准方案上点击发注，界面显示收件团队、授权素材和修订。任务包包含工程模型、立面 DXF、BOM、贴图、场景/机位、深度与色区、原始空拍、参考预览、用途和交期。发注用幂等键，断网重试共用订单号，提供已提交/已接单/校样/修改/交付/验收状态；将 8K 成品（例如双方约定 7680×4320）、色彩空间和审批记录回挂原版本。“一键”指数据交接，最终 CG 由蓝光团队制作与校样。

## 5　落到代码、接口与数据

以下目录和接口均为**拟新增**。首版可用纯 ES 模块承接现有 JS 数据；工程核写成独立、可在浏览器 Worker 和服务端同版本运行的模块，TypeScript 可作为开发语言。Python 负责项目、权限、文件、导出编排及异步任务。规则数学保持单一实现，避免一套 JS 预览和另一套 Python 计量各算各的。开发工具仅在隔离目录安装；面向客户交付预构建资源。

| 新组件 | 输入 → 输出 | 接入和隔离 |
|---|---|---|
| made-web/ | 项目编辑、2D/3D、方案比较、审签 | 独立页面与静态资源清单；经兼容测试的 2.0 渲染工具按固定版本引用或复制，保留许可证 |
| made-core/rules、geometry、solver | 已签规则包＋工程几何＋设计意图 → 编号格、板件多边形、构件、逐条判定 | 纯函数、定点单位或有版本的舍入约定；奇数毫米半跨及斜边交点保留精度到导出阶段；重叠区域取并集 |
| made-service/projects、reviews | 项目修订、角色、审批、素材索引 | 新服务根、专用配置和数据库；PoC 可单进程本地存储，企业版独立数据库和受控对象存储 |
| made-service/exports、jobs | 冻结结果 → DXF/XLSX/GLB/影像/CG 委托 | 任务按输入摘要去重，逐任务临时目录，校验通过后原子发布；超时、取消、断电后状态可恢复 |
| made-tests/、fixtures/ | 签认图纸、旧样例、错误输入 | 全套验证运行在隔离目录，输出差异报告和构建标识；用户 2.0 目录不作为测试目标 |

**项目与修订合同。** Project 保存项目 ID、图纸版本、单位、坐标变换、原始模型摘要和资产授权；Revision 保存父版本、geometry、faceGroup、floors、grid、feature、ruleset、catalog、locks、limits、seed；LayoutResult 保存 panel、piece、finish、stageTrace、exception 和逐面量。输出清单记录输入/结果摘要、单位、算法版本、物料表版本、机位、生成者与审核状态。草稿→校核→批准→归档；批准修订只读。多人保存按 expectedRevision 比对，冲突产生分支或提示合并；服务端校验权限和状态。旧文件中的型号、层数或墙绑定缺失时列为待确认，绝不从截图反推。

**新 API 示例。** 新服务以 `/api/made/v1` 为前缀。创建/读取项目，提交修订和条件校验，按 revisionId 计算与获取 resultId；使用 resultId 发起 export、compose、cg-order，查询 jobId 与下载受控产物。未授权、修订冲突、不可行、外部服务超时分别返回可区分状态。客户端将每次计算绑定到对应修订，切墙、切案后丢弃过期异步响应；重复点击发注或导出不重复计费。正式输出只读批准结果，草案导出带“検討用”。每一步都可回查到该板的规则与原始立面。

**旧项目互通。** 支持只读导入规则条件 JSON v1（version/fields）和自由方案 marq-pattern-v1。前者转成待复核的工程草稿，要求补楼层/墙面基准和模型绑定；后者作为视觉参考，不推断成合规工程排板。保存写入新项目文件或专用项目库，记录导入摘要和字段对照，旧文件可反复打开。新版本数据回到旧系统时可导出 PNG/展示 GLB；仅可表达的字段可另存 v1 副本并列出丢失项。迁移先校验临时副本再提交，失败保留原件和上一份可开的修订。

### 第五章的企业运行条件

企业 Web 服务从独立域名或经批准的新路径进入；试点本机使用未占用的独立回环端口，例如 8081，8080 继续提供旧版。正式版配置组织登录、项目级访问、制定者/设计/审核/营业/采购/CG 角色、短期下载授权、备份恢复和只记录必要元数据的审计。客户资料默认仅项目参与者可见，营业用户只复制已开放的设计变量。管理员发布规则需要第二人复核，新规则发布不给既有批准案自动重算。

文字与图像服务经独立服务端网关。按项目指定允许外发的素材、供应商、模型、端点、保留条件和区域。**“不用于训练”与“零保留”分别核验**；在签约、账号审批和适用端点确认前，使用本地确定性排板、本地合成和模板说明。关闭外发时覆盖网关、重试队列、日志、遥测和 CG 打包路径。日志避免原图、密钥与完整提示词；原档和成品依 GLP 自有留存政策管理。企业会话独立于 2.0 本地令牌，API 密钥仅存在新服务的机密配置。已有文本接口的成功响应不能证明图像端点获批。供应商条件需在上线时按实际项目复核。[OpenAI 官方数据控制说明](https://developers.openai.com/api/docs/guides/your-data)

## 8　评审后可直接开工的顺序

1. **蓝光开发**固化基线并建立独立工程目录、离线测试资产和可重复的打包流程。输出《基线功能清单》《输入与输出样例》。
2. **GLP 指南制定者＋蓝光建筑设计师**在同一张立面签署 C4/C6、反向走板、标识净空、雁行例外、实际跨与竖贴模宽不整除时的处理、面积分母。向采购取三厂家表及正式样板，向设计方取标识手册和批准 DWG/DXF/图纸。未关闭项可开展其他开发，以“待确认”标记依赖功能。
3. **规则与前端开发**先做一栋真实楼的工程快照、全周排板和逐板差异，再扩到上述五类及非常规尺寸；建立签过的金样，在每次规则更新自动重跑。
4. **采购、CG 和信息部门**分别签量表、图像保护区及交接包、登录权限与供应商数据条件。试点以两到三个真实项目验证投入，优先选一个含局部连窗的 BOX 和一个带坡道的项目。
5. **项目负责人**逐项签《需求—规则—用例—结果—负责人》台账，交付安装包、数据字典、版本清单、验收报告和恢复记录。批准范围限定到已测规则版本、设备和输入规模；新增地区、厂家或指南版本可单独补测发版。

**本次建议的评审决定**：采用双轨实施；按提案六大功能立项，以 Phase 1 的真实建筑和金样作为首笔开发验收；将企业影像外发、厂家订货和 8K 发注分别设为可独立启用的能力。这样 GLP 的人员可先验证自己的规则能否在不同建筑上正确运行，再按已经验证的业务收益扩大投入。
